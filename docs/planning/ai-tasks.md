# SERVIO — AI, RAG & ORCHESTRATION ENGINEER

## خطة تنفيذ مهندس الذكاء الاصطناعي خلال 4 أسابيع

### الهدف النهائي

بناء طبقة ذكاء اصطناعي متكاملة داخل Servio تستطيع تحليل حالات العملاء باستخدام أدلة قابلة للتتبع، واسترجاع المعلومات من المستندات، واكتشاف التعارضات، وإنتاج تقييم منظم، واقتراح الإجراءات المناسبة، مع التحقق من الاستشهادات والتكامل مع الـBackend.

السيناريو الأساسي هو Missing Delivery: عميل بيبلغ عن عدم استلام طلبه، ومصادر البيانات بتقدم معلومات متعارضة عن حالة الشحنة.

### التقنيات الأساسية

* Python 3.11.x.
* Pydantic.
* LLM Provider Abstraction.
* Mock Provider.
* DeepSeek-compatible adapter، مع إبقائه معطلًا افتراضيًا.
* BGE-M3 Embeddings.
* PostgreSQL Full-Text Search.
* pgvector.
* Reciprocal Rank Fusion (RRF).
* CitationGuard.
* Temporal Graph integration باستخدام PostgreSQL.
* LangGraph.
* Pytest وأدوات تقييم جودة الـAI.

**قواعد أساسية:** العمل داخل المشروع الموجود، والرجوع إلى `MASTER_PLAN.md` وقرارات المعمارية، واستخدام بيانات اصطناعية فقط، وعدم تكرار خدمات الـBackend أو إنشاء قاعدة بيانات جديدة.

# WEEK 1 — AI Foundation & Provider Layer

## 1. فحص المشروع وتجهيز AI Module

* مراجعة ملفات المشروع الحالية والمعمارية المعتمدة.
* فحص حزمة `servio_ai` وأي خدمات أو Schemas موجودة.
* تحديد المكونات التي يمكن إعادة استخدامها والمكونات الناقصة.
* تجهيز تنظيم واضح لملفات الـProviders والـSchemas والـServices والـTests.
* تجهيز طريقة تشغيل واختبار وحدة الـAI بصورة مستقلة عن الواجهة وقاعدة البيانات.

## 2. بناء LLM Provider Abstraction

* تجهيز واجهة `ChatModel` مستقلة عن مزود النموذج.
* دعم المخرجات المنظمة باستخدام Schema محدد.
* تجهيز معالجة أخطاء النموذج والمخرجات غير الصحيحة.
* فصل إعدادات مزود النموذج عن منطق تحليل الحالات.
* تصميم الواجهة بحيث يمكن تغيير المزود دون إعادة كتابة خدمات التحليل.

## 3. تجهيز Mock Provider

* بناء Mock Provider يعتمد على Fixtures ونتائج قابلة للتكرار.
* تجهيز حالات اختبار باللغة العربية والإنجليزية.
* دعم حالات نجاح التحليل وتعارض الأدلة وعدم كفايتها.
* ضمان عمل الاختبارات دون الإنترنت أو مفاتيح API.
* توفير Smoke Test للتأكد من أن المزود يعيد مخرجات صحيحة وفق الـSchema المطلوب.

## 4. تجهيز DeepSeek Provider

* تنفيذ أو استكمال OpenAI-compatible adapter وفق المعمارية المعتمدة.
* استخدام إعدادات المشروع لتحديد الـEndpoint واسم النموذج.
* إبقاء `SERVIO_DEEPSEEK_ENABLED=false` افتراضيًا.
* منع الاستدعاءات المدفوعة دون الموافقة المطلوبة.
* تطبيق قيود البيئة لمنع استخدام المزود المدفوع في الاختبارات وبيئة الـDemo.
* توثيق متطلبات تفعيل المزود ومحددات الخصوصية والتكلفة.

لا تُفعّل DeepSeek ولا تُجرِ أي استدعاء مدفوع خلال تنفيذ هذه الخطة دون موافقة صريحة منفصلة.

## 5. تجهيز Schemas الخاصة بالـAI

الاتفاق مع مهندس الـBackend على نماذج موحدة تشمل:

* `CaseInput`
* `EvidenceItem`
* `CaseAssessment`
* `ConflictRecord`
* `ActionProposal`

يجب أن تتضمن النماذج ما يلزم من معرفات الحالة والأدلة ومصادر المعلومات وحالة التقييم والمعلومات الناقصة والإجراء المقترح.

تُستخدم نماذج الـBackend الموجودة إن كانت مناسبة، بدلًا من إنشاء تعريفات مكررة.

## 6. بناء أول Missing Delivery Prototype

* استقبال بيانات حالة تجريبية ومجموعة من الأدلة.
* إنتاج ملخص منظم للحالة.
* تحديد التعارضات والمعلومات الناقصة.
* إرجاع مراجع الأدلة الموجودة فعلًا.
* التمييز بين الأدلة الكافية والأدلة غير الكافية.
* اقتراح الإجراء المناسب دون تنفيذه.

## التسليم المطلوب بنهاية الأسبوع الأول

* AI Module منظم.
* `ChatModel` Interface.
* Mock Provider يعمل دون اتصال.
* أساس DeepSeek adapter مع تعطيله افتراضيًا.
* Schemas متفق عليها مع الـBackend.
* Missing Delivery Prototype.
* Fixtures بالعربية والإنجليزية.
* اختبارات أولية للـProvider والـSchemas والتحليل.
* توثيق واجهة التكامل مع الـBackend.

**معيار القبول:** تشغيل حالة Missing Delivery اصطناعية وإرجاع Assessment منظم، مع مراجع أدلة صحيحة، دون الحاجة إلى API مدفوع.

# WEEK 2 — Document Processing, BGE-M3 & Hybrid RAG

## 1. تجهيز Document Processing

* بناء أو استكمال خدمة معالجة المستندات.
* دعم PDF وDOCX وCSV وXLSX وفق متطلبات المشروع.
* استخراج النصوص والـMetadata اللازمة.
* تطبيع النصوص العربية بما لا يغيّر معناها.
* تقسيم النص إلى Chunks مناسبة للبحث.
* إنشاء IDs ثابتة للمستندات والمقاطع.
* الاحتفاظ بمعلومات المصدر والصفحة أو الورقة عند توفرها.
* تسجيل حالات نجاح المعالجة وفشلها بصورة واضحة.

لا يدخل OCR للمستندات المصورة ضمن النطاق الأساسي لهذه المرحلة.

## 2. تجهيز BGE-M3 Embeddings

* تجهيز واجهة `EmbeddingModel`.
* ربطها بنموذج BGE-M3 المحلي.
* تجهيز تحميل النموذج وتشغيله بصورة منفصلة عن منطق التطبيق.
* دعم المعالجة على دفعات حيثما أمكن.
* توفير Fake Embedder للاختبارات.
* التحقق من أبعاد الـEmbeddings قبل تخزينها.
* التعامل بوضوح مع عدم توفر أوزان النموذج أو تعذر تشغيله في البيئة المحلية.

يجب الالتزام بأبعاد النموذج المحددة في المشروع، وهي 1024 بُعدًا للـBGE-M3 في الخطة المعتمدة.

## 3. بناء Hybrid Retrieval

تجهيز البحث باستخدام مصدرين:

**Semantic Search**

* استخدام pgvector لاسترجاع المقاطع ذات الصلة الدلالية.

**Full-Text Search**

* استخدام PostgreSQL Full-Text Search لاسترجاع المقاطع ذات الصلة بالكلمات والمصطلحات.

**Rank Fusion**

* دمج النتائج باستخدام RRF.
* إزالة النتائج المكررة.
* الحفاظ على معرف المقطع ومصدره وترتيبه في النتائج النهائية.
* دعم الاستعلامات العربية والإنجليزية.
* التعامل مع عدم وجود نتائج من أحد مصدري البحث.

## 4. التكامل مع الـBackend

* الاتفاق على واجهة استدعاء خدمة البحث.
* استقبال Tenant Context معتمد من الـBackend.
* الالتزام بآليات عزل البيانات الموجودة في قاعدة البيانات.
* إرجاع الأدلة في صيغة يستطيع الـBackend والـFrontend استهلاكها.
* عدم تجاوز RLS أو إنشاء اتصال بقاعدة البيانات بصلاحيات غير معتمدة.
* عدم إنشاء خدمة استرجاع بديلة إذا كانت هناك خدمة قائمة بالفعل.

## 5. تقييم أولي لجودة البحث

* تجهيز مجموعة استعلامات اصطناعية.
* تحديد المقاطع الصحيحة لكل استعلام.
* اختبار نتائج Semantic Search وFull-Text Search والبحث الهجين.
* قياس Recall@10 عندما تتوفر البيانات اللازمة.
* فحص التكرار وجودة الترتيب.
* إضافة اختبارات لاستعلامات عربية وإنجليزية.

## التسليم المطلوب بنهاية الأسبوع الثاني

* Document Processing Service.
* Chunking مع IDs ثابتة ومعلومات المصدر.
* واجهة BGE-M3 Embeddings وتكامل محلي قابل للاختبار.
* Hybrid Retrieval باستخدام pgvector وPostgreSQL FTS.
* دمج النتائج باستخدام RRF.
* واجهة واضحة للـBackend لاسترجاع الأدلة.
* اختبارات للبحث العربي والإنجليزي وجودة النتائج.
* تقرير أولي لجودة الاسترجاع.

**معيار القبول:** رفع مستند اصطناعي ومعالجته، ثم البحث داخله وإرجاع مقاطع مرتبطة بالمصدر ومعرفات قابلة للاستخدام في تحليل الحالة والاستشهاد بها.

# WEEK 3 — CitationGuard, Conflict Detection & LangGraph

## 1. بناء CitationGuard

* إنشاء خدمة مستقلة للتحقق من الاستشهادات.
* التأكد من أن كل Evidence ID مستخدم في التقييم موجود فعلًا ضمن الأدلة المقدمة.
* اكتشاف المراجع غير الصحيحة أو غير الموجودة.
* التحقق من ارتباط الاستشهاد بالـEvidence Collection الخاصة بالحالة.
* رفض أو تسجيل أي مرجع غير صحيح وفق سياسة المشروع.
* التمييز بين صحة المرجع من الناحية التقنية وصحة الادعاء من الناحية الدلالية.
* إظهار الأخطاء في نتيجة منظمة يسهل اختبارها وعرضها.

لا تُعتبر الإجابة صحيحة تلقائيًا لمجرد أن معرف الدليل موجود.

## 2. بناء Conflict Detection

* تجهيز خدمة لاكتشاف التعارضات بين الادعاءات المتعلقة بالكيان أو الحدث نفسه.
* مقارنة الحالات والتواريخ والمعلومات التي توفرها المصادر.
* الحفاظ على طرفي التعارض ومصدر كل معلومة.
* التمييز بين التعارض الحقيقي والمعلومات الناقصة.
* مراعاة قواعد أولوية المصادر الموجودة في المشروع.
* عدم افتراض أن أحدث معلومة هي الصحيحة دائمًا.
* إرجاع `ConflictRecord` منظم يحتوي على الأدلة والادعاءات المرتبطة.

أمثلة الاختبار:

* شركة الشحن تقول Delivered، بينما توجد أدلة متعارضة.
* مصدران يقدمان توقيتين مختلفين للحدث نفسه.
* مصادر تقدم معلومات متوافقة لا يجب تصنيفها كتعارض.
* المعلومات غير المكتملة التي لا تكفي للحسم.

## 3. التكامل مع Temporal Graph

* فحص واجهات `GraphRepository` التي يوفرها الـBackend.
* استهلاك خدمات `timeline` و`neighborhood` و`state_as_of` عند توفرها.
* تجهيز خدمة AI-facing interface تستقبل سياق الرسم البياني.
* الحفاظ على التواريخ ومراجع المصادر.
* الالتزام بحدود عمق الاستعلام.
* استخدام Fake Graph Repository للاختبارات إذا لم تكتمل الخدمة بعد.

**المسؤولية هنا هي استهلاك خدمات الرسم البياني من الـBackend، وليس بناء قاعدة Graph مستقلة أو اعتماد Neo4j دون موافقة.**

## 4. بناء LangGraph Case Resolution

تجهيز أو استكمال Workflow باسم `case_resolution` يتضمن المراحل المناسبة من:

1. Intake.
2. Context Resolution.
3. Evidence Retrieval.
4. Conflict Analysis.
5. Policy Analysis عند توفر الأدلة والسياسات المطلوبة.
6. Assessment.
7. CitationGuard.
8. Action Planning.
9. Respond أو Clarify أو Escalate.

يجب الفصل بين مهام الـLLM والخدمات الحتمية.

الـLLM مسؤول عن الفهم والاستخراج والتحليل المنظم واقتراح الإجراءات. أما التحقق من الصلاحيات والموافقة والتنفيذ والتحقق من النتيجة، فمسؤولية الـBackend.

## 5. تجهيز حدود الـWorkflow

* وضع حدود لعدد الخطوات واستدعاءات النموذج والوقت.
* التعامل مع أخطاء العقد أو الاسترجاع.
* دعم إنهاء الـWorkflow عند عدم كفاية الأدلة.
* منع التكرار غير المنضبط في الانتقال بين المراحل.
* تسجيل حالة التشغيل والأخطاء بطريقة تسمح بعرضها في الواجهة.
* استخدام آلية Checkpointing الموجودة في المشروع عند توفرها.
* الحفاظ على عزل سياق الـTenant عند حفظ حالة التشغيل واستعادتها.

## 6. الاختبارات

* اختبار نجاح تحليل Missing Delivery.
* اختبار التعارضات.
* اختبار عدم كفاية الأدلة.
* اختبار الاستشهادات غير الصحيحة.
* اختبار محتوى الأدلة الذي يحتوي على تعليمات غير موثوقة.
* اختبار فشل الاسترجاع أو فشل أحد الـNodes.
* التأكد من عدم تنفيذ إجراءات تجارية داخل الـWorkflow.

## التسليم المطلوب بنهاية الأسبوع الثالث

* CitationGuard.
* Conflict Detection Service.
* تكامل أو واجهة واضحة للـTemporal Graph.
* `case_resolution` Workflow.
* مخرجات Assessment موثقة بالأدلة.
* دعم Clarification وEscalation.
* اختبارات للسلامة وجودة الاستشهادات وحدود التنفيذ.
* توثيق عقد التكامل مع الـBackend والـFrontend.

**معيار القبول:** تشغيل Missing Delivery من خلال الـWorkflow، واسترجاع الأدلة، واكتشاف التعارضات، وإنتاج Assessment منظم، والتحقق من الاستشهادات، دون تنفيذ أي إجراء تجاري.

# WEEK 4 — Evaluation, Market Intelligence, Idea Intelligence & Integration

## 1. تجهيز Evaluation Runner

* بناء أو استكمال أداة لتشغيل تقييمات مكونات الـAI.
* دعم تحميل Dataset محدد.
* تشغيل المكون أو الـWorkflow المطلوب.
* مقارنة النتيجة بالمخرجات المتوقعة عندما تتوفر Labels.
* حساب المقاييس التي يمكن حسابها فعليًا.
* حفظ النتائج بصيغة قابلة للقراءة الآلية مثل JSON.
* إظهار الحالات التي فشلت وأسبابها.
* إرجاع حالة فشل واضحة عندما تفشل الاختبارات المطلوبة.

يجب ألا تعتمد التقييمات الروتينية على API مدفوع.

## 2. تجهيز مجموعات التقييم

مراجعة المجموعات الموجودة وإنشاء أو استكمال:

* `ccrb-v1`
* `retrieval-v1`
* `market-v1`
* `idea-v1`

وفق الخطة، تستهدف المجموعات 60 حالة Case Resolution، و120 استعلام Retrieval، و15 حالة Market Research، و10 حالات Idea Analysis.

المطلوب:

* بيانات اصطناعية فقط.
* حالات بالعربية والإنجليزية.
* حالات تعارض أدلة وعدم كفايتها.
* حالات استشهاد غير صحيح.
* حالات Prompt Injection.
* حالات تتطلب Clarification أو Escalation.

لا تُملأ مجموعات التقييم بنسخ مكررة لمجرد تحقيق العدد المطلوب. سجّل العدد الفعلي وأي حالات ناقصة.

## 3. قياس الأداء والجودة

تجهيز المقاييس التي تدعمها البيانات والـLabels المتاحة، ومنها:

* Recall@10.
* nDCG@10 عندما تتوفر بيانات الصلة المطلوبة.
* Citation Reference Correctness.
* Unsupported Evidence References.
* Conflict Detection Precision وRecall وF1 عند توفر Ground Truth.
* Structured Output Validation Rate.
* Workflow Completion Rate.
* Correct Insufficient-Evidence Behavior.

مستهدفات الخطة الأولية للبحث تشمل Recall@10 ≥ 0.85 وnDCG@10 ≥ 0.70. هذه مستهدفات وليست نتائج مضمونة؛ يجب تشغيل التقييم وتسجيل النتائج الفعلية.

## 4. تجهيز Market Research Workflow

* بناء أو استكمال `market_research`.
* استقبال سؤال بحث.
* استخدام الأدلة الاصطناعية أو مصادر البحث المعتمدة في المشروع.
* إرجاع نتائج منظمة مع مراجع المصادر.
* تشغيل CitationGuard على المخرجات.
* إظهار نقص الأدلة أو القيود بوضوح.
* عدم اختلاق نتائج بحث مباشر أو إضافة خدمة بحث مدفوعة.

## 5. تجهيز Idea Analysis Workflow

* بناء أو استكمال `idea_analysis`.
* استقبال وصف الفكرة.
* تحليل المعلومات المتاحة.
* إرجاع تقييم أولي منظم وواضح.
* توضيح الأساس المستخدم في التقييم.
* الحفاظ على مراجع الأدلة.
* اكتشاف المخرجات غير المدعومة أو المعلومات الناقصة.

## 6. التكامل النهائي مع الـBackend والـFrontend

* استكمال واجهات استدعاء الـWorkflows.
* توحيد صيغ Assessment وEvidence وAction Proposal.
* تمرير الاستشهادات ومعلومات المصادر في المخرجات.
* تجهيز حالات الخطأ والنتائج غير المكتملة.

**معيار القبول النهائي:** يستطيع النظام تحليل Missing Delivery باستخدام الأدلة المتاحة، واسترجاع المعلومات من المصادر المحددة، وإنتاج تقييم قابل للتحقق من استشهاداته، واكتشاف التعارضات، ثم اقتراح إجراء مناسب دون تجاوز حدود الصلاحيات أو تنفيذ إجراء تجاري بنفسه.

# قواعد التنفيذ والتسليم

1. افحص الموجود قبل إنشاء أي Module أو Service جديد.
2. لا تكرر خدمات أو Schemas يملكها الـBackend.
3. استخدم Mock Provider كخيار افتراضي للاختبارات والـDemo.
4. لا تفعّل DeepSeek أو أي خدمة مدفوعة دون الموافقة المطلوبة.
5. لا تستخدم بيانات عملاء حقيقية.
6. حافظ على IDs الأدلة ومعلومات المصدر طوال خط المعالجة.
7. لا تسمح للـLLM باتخاذ قرارات التفويض أو تنفيذ الإجراءات.
8. لا تعتمد على نتائج وهمية باعتبارها تكاملًا حقيقيًا.
9. عندما تكون خدمة الـBackend غير جاهزة، استخدم Interface أو Fake Implementation واضحًا واختبره.
10. أعطِ الأولوية لسيناريو Missing Delivery قبل التوسع في الوظائف الثانوية.
11. لا تعتبر أي ميزة مكتملة بمجرد كتابة ملفاتها؛ يجب التحقق من تشغيلها واختبارها.
12. في نهاية كل أسبوع، سلّم نسخة قابلة للاختبار، واكتب ما تم إنجازه وما لا يزال معطلًا أو مؤجلًا.

## التقرير المطلوب في نهاية كل أسبوع

* المكونات المكتملة.
* الملفات الجديدة والمعدلة.
* الاختبارات التي تم تشغيلها ونتائجها.
* حالة التكامل مع الـBackend والـFrontend.
* نتائج تقييم الجودة المتاحة.
* المشاكل المعروفة.
* المهام المتبقية للأسبوع التالي.
* أي اعتماد على خدمة خارجية أو موافقة لم يتم استكمالها.

# الاتفاقات المشتركة بين المهندسين

## في نهاية الأسبوع الأول

* الـBackend يوفّر APIs وعقد بيانات واضحًا.
* الـAI يوفّر Schemas وMock Provider ونتيجة تحليل تجريبية منظمة.
* الـFrontend يوفّر Customer 360 مبدئيًا متصلًا بالبيانات.

## في نهاية الأسبوع الثاني

* البيانات تصل من المصادر التجريبية إلى الـBackend.
* خدمة البحث تعيد أدلة قابلة للتتبع.
* الواجهة تعرض بيانات العميل والأدلة والمصادر.

## في نهاية الأسبوع الثالث

* الـAI يحلل الحالة ويكتشف التعارضات ويقترح إجراءً.
* الـBackend يطبّق قواعد الأمان والموافقة والتنفيذ التجريبي.
* الـFrontend يعرض التحليل وسير العمل والموافقة.

## في نهاية الأسبوع الرابع

* الثلاثة يشغّلون سيناريو Missing Delivery كاملًا.
* يتم اختبار النتائج وحالات الفشل والصلاحيات.
* تُجهّز نسخة Demo مستقرة مع توثيق القيود والمتطلبات المتبقية.

# قواعد تقسيم الشغل

1. كل مهندس مسؤول عن تخصصه، لكن الـAPI Contracts والـSchemas مشتركة بين الفريق.
2. لا ينتظر مهندس انتهاء باقي الفريق بالكامل؛ يبدأ باستخدام Interfaces وTest Doubles متفق عليها.
3. لا يُعتبر أي مكوّن منتهيًا لمجرد إنشاء ملفاته؛ يجب تشغيله واختباره.
4. الأولوية لسيناريو Missing Delivery قبل التوسع في الوظائف الثانوية.
5. لا يُفعّل أي API مدفوع دون الموافقة المطلوبة، ويظل الـMock Provider هو الخيار الافتراضي.
6. تبقى صلاحيات المستخدمين والموافقة والتنفيذ والتحقق النهائي مسؤولية الـBackend، وليس الـLLM.
7. لا يتم نشر الواجهة للعامة قبل استكمال قرار G-WEB ومتطلباته.
8. في نهاية كل أسبوع، يجرّب المهندسون الثلاثة نسخة واحدة متكاملة ويسجلون الأخطاء التي ستدخل في خطة الأسبوع التالي.
