# SERVIO — مهام مهندس الـBackend, Data & Platform

**مدة التنفيذ: 4 أسابيع**

**المسؤولية الأساسية:** قاعدة البيانات، الـAPIs، الأمان، مصادر البيانات، وتنفيذ الإجراءات من خلال الـBackend.

---

## Week 1 — Backend Foundation

* تجهيز مشروع FastAPI والـConfiguration والـEnvironment.
* تجهيز Supabase/PostgreSQL وملفات الـMigrations.
* تصميم الجداول الأساسية للعملاء والطلبات والشحنات والتذاكر.
* تجهيز الأساس الخاص بالـTenants والـMemberships والصلاحيات.
* وضع أساس الـRLS وعزل بيانات كل Tenant.
* تجهيز API Contract واضح لمهندس الـFrontend ومهندس الـAI.
* إنشاء بيانات تجريبية لسيناريو Missing Delivery.

**التسليم:** Backend يعمل محليًا، وقاعدة بيانات أولية، وواجهات API موثقة، وعقد بيانات متفق عليه مع باقي الفريق.

---

## Week 2 — Connectors & Customer Data

* بناء إطار عمل موحد للـMock Connectors.
* تجهيز مصادر Orders وCourier Tracking وSupport Desk وبيانات Payments وDocuments اللازمة للعرض.
* تجهيز تحميل البيانات وتخزينها مع منع تكرار السجلات.
* إضافة حالة تشغيل الـConnectors والأخطاء وإعادة المحاولة.
* استكمال APIs الخاصة بالعميل والطلبات والشحنات والتذاكر.
* تجهيز خدمات Customer 360.
* تجهيز الجداول والخدمات الأساسية للـCases وCase Events.

**التسليم:** البيانات التجريبية تُحمّل من المصادر المختلفة، والـFrontend يستطيع عرض ملف عميل موحد يحتوي على بيانات المصادر الثلاثة.

---

## Week 3 — Cases, Actions & Approvals

* تجهيز خدمات إدارة الحالات وتغيير حالتها وتعيين المسؤول عنها.
* تجهيز أساس سياسات الإجراءات وتصنيف مستوى المخاطر.
* بناء Action Catalog للإجراءات المسموح بها.
* بناء خدمات Approval Center وحالات الموافقة والرفض.
* تطبيق Idempotency لمنع تكرار تنفيذ الإجراء.
* تجهيز آلية التنفيذ على Mock Connectors.
* تجهيز التحقق من نتيجة التنفيذ ومعالجة الحالات غير المؤكدة.
* ربط قرارات الموافقة والرفض بسجلات التدقيق.

**التسليم:** الـBackend يدعم دورة حياة الحالة، واقتراح الإجراءات، والموافقة عليها، وتنفيذها بصورة تجريبية آمنة، والتحقق من النتيجة.

---

## Week 4 — Integration, Consoles & Hardening

* استكمال التكامل مع مهندس الـAI والـFrontend.
* تجهيز APIs اللازمة للـSupervisor Console وPlatform Admin Console.
* تجهيز البيانات التي تعتمد عليها مؤشرات الأداء وحالة الـConnectors وسير العمل والموافقات.
* إكمال اختبارات الصلاحيات وعزل بيانات الـTenants.
* اختبار حالات فشل الـConnectors وإعادة المحاولة ومنع التكرار.
* مراجعة إعدادات التشغيل وDocker حسب الخطة.
* توثيق طريقة تشغيل الـBackend والاختبارات وإعدادات الـDemo.

**التسليم النهائي:** Backend متكامل مع الـAI والـFrontend، مع APIs واختبارات أساسية تسمح بتشغيل سيناريو Missing Delivery بالكامل.

---

# الاتفاقات المشتركة بين المهندسين

## في نهاية الأسبوع الأول

* الـBackend يوفّر APIs وعقد بيانات واضحًا.
* الـAI يوفّر Schemas وMock Provider ونتيجة تحليل تجريبية منظمة.
* الـFrontend يوفّر Customer 360 مبدئيًا متصلًا بالبيانات.

## في نهاية الأسبوع الثاني

* البيانات تصل من المصادر التجريبية إلى الـBackend.
* خدمة البحث تعيد أدلة قابلة للتتبع.
* الواجهة تعرض بيانات العميل والأدلة والمصادر.

## في نهاية الأسبوع الثالث

* الـAI يحلل الحالة ويكتشف التعارضات ويقترح إجراءً.
* الـBackend يطبّق قواعد الأمان والموافقة والتنفيذ التجريبي.
* الـFrontend يعرض التحليل وسير العمل والموافقة.

## في نهاية الأسبوع الرابع

* الثلاثة يشغّلون سيناريو Missing Delivery كاملًا.
* يتم اختبار النتائج وحالات الفشل والصلاحيات.
* تُجهّز نسخة Demo مستقرة مع توثيق القيود والمتطلبات المتبقية.

---

# قواعد تقسيم الشغل

1. كل مهندس مسؤول عن تخصصه، لكن الـAPI Contracts والـSchemas مشتركة بين الفريق.
2. لا ينتظر مهندس انتهاء باقي الفريق بالكامل؛ يبدأ باستخدام Interfaces وTest Doubles متفق عليها.
3. لا يُعتبر أي مكوّن منتهيًا لمجرد إنشاء ملفاته؛ يجب تشغيله واختباره.
4. الأولوية لسيناريو Missing Delivery قبل التوسع في الوظائف الثانوية.
5. لا يُفعّل أي API مدفوع دون الموافقة المطلوبة، ويظل الـMock Provider هو الخيار الافتراضي.
6. تبقى صلاحيات المستخدمين والموافقة والتنفيذ والتحقق النهائي مسؤولية الـBackend، وليس الـLLM.
7. لا يتم نشر الواجهة للعامة قبل استكمال قرار G-WEB ومتطلباته.
8. في نهاية كل أسبوع، يجرّب المهندسون الثلاثة نسخة واحدة متكاملة ويسجلون الأخطاء التي ستدخل في خطة الأسبوع التالي.
