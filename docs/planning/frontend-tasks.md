# SERVIO — FRONTEND & BILINGUAL UI ENGINEER

## خطة تنفيذ الواجهة الأمامية خلال 4 أسابيع

**الهدف النهائي:** بناء واجهة Servio باستخدام Next.js، تدعم العربية والإنجليزية، وتتصل بالـBackend APIs، وتعرض بيانات العملاء والأدلة وتحليل الـAI والإجراءات والموافقات، مع تجهيز الـConsoles واختبارات الـDemo.

### التقنيات الأساسية

* Next.js وReact وفق إصدارات المشروع المعتمدة.
* TypeScript.
* `next-intl` لدعم العربية والإنجليزية.
* REST APIs موثقة باستخدام OpenAPI.
* Playwright لاختبارات الواجهة.
* أدوات الاختبار والمكونات الموجودة بالفعل في المشروع.

**تعليمات أساسية:** قبل تنفيذ أي Task، افحص المشروع وملف `MASTER_PLAN.md`، واستكمل الموجود بدلًا من إنشاء واجهة أو مكونات مكررة. لا تغيّر قرارات المعمارية أو إصدارات التقنيات من نفسك.

# WEEK 1 — Frontend Foundation & Core Screens

## المهام المطلوبة

### 4. تجهيز App Shell والتنقل

* تجهيز أساس Tenant Switcher إذا كانت واجهة العضويات متاحة من الـBackend.

* إظهار رقم الحالة والعميل ونوع المشكلة والحالة الحالية.
* تجهيز البحث والفلترة الأساسيين إذا كانت APIs تدعمهما.
* دعم الانتقال من الحالة إلى شاشة التفاصيل.
* عرض حالات Loading وError وEmpty.
* عدم وضع أرقام أو حالات وهمية على أنها بيانات فعلية.

### 6. بناء شاشة Customer 360

* عرض بيانات العميل الأساسية.
* عرض الطلبات والشحنات والتذاكر المتاحة.
* إظهار مصدر البيانات لكل مجموعة من المعلومات.
* تجهيز منطقة لعرض التعارضات.
* تجهيز منطقة لعرض الـTimeline عندما توفرها الـBackend APIs.
* ربط الشاشة بالـAPI Client بدلًا من الاعتماد على بيانات مكتوبة داخل مكونات الواجهة.

## التسليم المطلوب بنهاية الأسبوع الأول

* دعم العربية والإنجليزية واتجاهي RTL/LTR.

# WEEK 2 — Connectors, Evidence & Customer Timeline

## المهام المطلوبة

### 1. استكمال Customer 360

* استكمال عرض الطلبات والشحنات والتذاكر والمعاملات المتاحة.

* تحسين تجربة الانتقال بين العميل والحالات المرتبطة به.

### 2. بناء Connector Management Screen

* عرض قائمة مصادر البيانات التجريبية.
* إظهار نوع المصدر وحالته وآخر تشغيل وفق البيانات المتاحة.
* تجهيز زر تشغيل Connector عندما يتوفر الـAPI اللازم.
* عرض حالة تحميل البيانات وتقدم التشغيل إذا توفر من الـBackend.
* عرض أعداد السجلات وحالة النجاح والفشل.
* إظهار رسائل مفهومة عند فشل المصدر أو تعذر إعادة المحاولة.
* عدم عرض نجاح تحميل البيانات ما لم يؤكده الـBackend.

### 3. بناء Evidence Explorer

* عرض الأدلة والمقاطع المسترجعة من الـAI أو الـBackend.

* تمييز الأدلة المرتبطة بتعارض معين.
* توضيح حالات عدم وجود نتائج أو عدم كفاية الأدلة.
* تجهيز الانتقال بين الدليل والحالة التي تستخدمه.

### 4. بناء عرض الـTimeline والبيانات التاريخية

* عرض الأحداث حسب التوقيت المتاح في البيانات.
* التمييز بين وقت وقوع الحدث ووقت تسجيله إذا كان الـAPI يعرضهما.
* توفير عرض واضح للعلاقة بين العميل والطلب والشحنة والأحداث.
* عرض حالة تاريخية عندما تدعمها واجهات الـBackend.

### 5. استكمال حالات الواجهة

* إضافة Loading وEmpty وError States إلى الشاشات الجديدة.
* التعامل مع حالات انتهاء الجلسة وأخطاء الاتصال.
* عرض حالات عدم التصريح بالوصول بصورة واضحة.
* اختبار العرض بالعربية والإنجليزية.

# WEEK 3 — Case Intelligence, Workflow Monitor & Approval Center

## المهام المطلوبة

### 1. بناء شاشة تفاصيل الحالة Case Details

* عرض بيانات الحالة والعميل المرتبط بها.
* عرض وصف المشكلة وبيانات الطلب والشحنة المتاحة.
* عرض ملخص تحليل الـAI.
* عرض الأدلة والاستشهادات المرتبطة بالتحليل.
* إظهار التعارضات التي اكتشفها النظام.
* إظهار المعلومات الناقصة التي تتطلب توضيحًا.
* عرض حالة الحالة والإجراء التالي وفق ما يرجعه الـBackend.

### 2. عرض نتيجة تحليل الـAI

* عرض الـAssessment المنظم بصورة سهلة القراءة.
* إظهار الأدلة بجوار الادعاءات التي تدعمها عندما تكون العلاقة موجودة في البيانات.
* توفير انتقال إلى مصدر الدليل.
* عرض حالة Insufficient Evidence بصورة واضحة.
* التمييز بين النتيجة المؤكدة والنتيجة التي تحتاج إلى تحقيق إضافي.
* عرض Clarification أو Escalation عندما يرجعهما الـBackend أو الـAI Workflow.
* عدم إظهار الادعاءات غير المدعومة باعتبارها حقائق مؤكدة.

### 3. بناء Workflow Monitor

* عرض قائمة تشغيلات الـWorkflow.
* إظهار الحالة الحالية لكل تشغيل.
* عرض Success وFailed وRunning وغيرها من الحالات التي يدعمها الـBackend.
* عرض مراحل التنفيذ والأخطاء وإعادات المحاولة المتاحة.
* تجهيز صفحة أو جزء لتفاصيل التشغيل.
* ربط المعلومات بالبيانات الفعلية بدلًا من عرض مؤشرات أو مراحل ثابتة توحي بوجود تنفيذ حقيقي.

### 4. بناء Approval Center

* عرض الإجراءات التي تنتظر الموافقة.
* إظهار نوع الإجراء والسبب والمعاملات والأدلة ومستوى المخاطر عندما توفرها الـAPI.
* عرض الحالات المختلفة للموافقة.
* تجهيز تفاصيل طلب الموافقة وسجل التغييرات.
* إضافة أزرار Approve وReject وفق الصلاحيات والـAPI المتاحين.
* إظهار نتيجة العملية ورسائل الخطأ بصورة واضحة.
* تحديث الواجهة بعد نجاح العملية بما يتوافق مع استجابة الـBackend.

**قاعدة أساسية:** الواجهة لا تقرر إذا كان المستخدم مسموحًا له بالموافقة، ولا تنفذ الإجراء التجاري بنفسها. الـBackend هو المسؤول عن التحقق من الصلاحيات والموافقة والتنفيذ.

### 5. تحسين Cases Queue

* عرض حالة كل Case وفق البيانات المتاحة.
* تجهيز واجهة التعيين والمسؤول عن الحالة إذا توفرت APIs اللازمة.
* عرض أولوية الحالة وبيانات الـSLA عندما يوفرها الـBackend.
* تجهيز البحث والفلترة والترتيب وفق القدرات التي يدعمها الـAPI.
* تحسين الانتقال بين قائمة الحالات والتفاصيل والأدلة والموافقات.

### 6. اختبار التكامل مع الـAI والـBackend

* اختبار عرض Assessment فعلي من الـAPI.
* اختبار حالة نجاح التحليل وحالة فشله.
* اختبار وجود أدلة وحالة عدم كفايتها.
* اختبار تحديث حالة الموافقة.
* إصلاح اختلافات البيانات بين المكونات والـAPI Contracts.

## التسليم المطلوب بنهاية الأسبوع الثالث

* Case Details Screen.
* عرض تحليل الـAI والأدلة والاستشهادات.
* Workflow Monitor.
* Approval Center.

# 4. قواعد التنفيذ والتسليم

1. استخدم API Contracts الموجودة في المشروع، ولا تنشئ نماذج بيانات مكررة.
2. لا تتصل بقاعدة البيانات مباشرة من الواجهة؛ استخدم الـBackend APIs وفق بنية المشروع.
3. لا تضع صلاحيات المستخدمين أو قواعد الموافقة داخل الواجهة باعتبارها مصدر القرار النهائي.
4. لا تعرض بيانات أو أرقامًا وهمية باعتبارها بيانات حقيقية.
5. اختبر جميع الصفحات الأساسية بالعربية والإنجليزية.
6. حافظ على اتساق مكونات الواجهة، وتجنب تكرار الكود.
7. لا تعتبر الصفحة مكتملة لمجرد أن شكلها جاهز؛ يجب اختبارها مع الـAPI أو Mock Contract واضح.
8. إذا تأخر الـBackend، استخدم Mock API مؤقتًا مع توثيق الحقول المتوقعة، ثم اربط الخدمة الفعلية بمجرد توفرها.
9. أعطِ الأولوية لمسار Missing Delivery قبل التوسع في الشاشات الثانوية.
10. في نهاية كل أسبوع، سلّم نسخة تعمل محليًا مع قائمة بالتاسكات المكتملة والاختبارات والأخطاء المتبقية.

# الاتفاقات المشتركة بين المهندسين

## في نهاية الأسبوع الأول

* الـBackend يوفّر APIs وعقد بيانات واضحًا.
* الـAI يوفّر Schemas وMock Provider ونتيجة تحليل تجريبية منظمة.
* الـFrontend يوفّر Customer 360 مبدئيًا متصلًا بالبيانات.

## في نهاية الأسبوع الثاني

* البيانات تصل من المصادر التجريبية إلى الـBackend.
* خدمة البحث تعيد أدلة قابلة للتتبع.
* الواجهة تعرض بيانات العميل والأدلة والمصادر.

## في نهاية الأسبوع الثالث

* الـAI يحلل الحالة ويكتشف التعارضات ويقترح إجراءً.
* الـBackend يطبّق قواعد الأمان والموافقة والتنفيذ التجريبي.
* الـFrontend يعرض التحليل وسير العمل والموافقة.

## في نهاية الأسبوع الرابع

* الثلاثة يشغّلون سيناريو Missing Delivery كاملًا.
* يتم اختبار النتائج وحالات الفشل والصلاحيات.
* تُجهّز نسخة Demo مستقرة مع توثيق القيود والمتطلبات المتبقية.

# قواعد تقسيم الشغل

1. كل مهندس مسؤول عن تخصصه، لكن الـAPI Contracts والـSchemas مشتركة بين الفريق.
2. لا ينتظر مهندس انتهاء باقي الفريق بالكامل؛ يبدأ باستخدام Interfaces وTest Doubles متفق عليها.
3. لا يُعتبر أي مكوّن منتهيًا لمجرد إنشاء ملفاته؛ يجب تشغيله واختباره.
4. الأولوية لسيناريو Missing Delivery قبل التوسع في الوظائف الثانوية.
5. لا يُفعّل أي API مدفوع دون الموافقة المطلوبة، ويظل الـMock Provider هو الخيار الافتراضي.
6. تبقى صلاحيات المستخدمين والموافقة والتنفيذ والتحقق النهائي مسؤولية الـBackend، وليس الـLLM.
7. لا يتم نشر الواجهة للعامة قبل استكمال قرار G-WEB ومتطلباته.
8. في نهاية كل أسبوع، يجرّب المهندسون الثلاثة نسخة واحدة متكاملة ويسجلون الأخطاء التي ستدخل في خطة الأسبوع التالي.
